    教练：## 知识整理：asyncio 与并发

    **主题**：asyncio 用 async/await 提供 I/O 并发，与 CPU 并行不同。

    **知识点与关系**

    1. **asyncio 的用途**：asyncio 是 Python 编写并发代码的库，核心基于 async/await 语法，适合 I/O 密集与网络任务。

    2. **工作原理**：协程（async 函数）遇到等待（如 I/O 操作）时，会把执行权让给事件循环，事件循环再调度其他**可运行**的任务。这样单个线程内可以有多个任务交错推进，实现“等待时不空转”。

    3. **并发 ≠ 并行**：
       - **并发**：多个任务**在同一时间段内**交替推进（逻辑上可能在同一线程内交错）。
       - **并行**：多个任务**在同一时刻**由多个 CPU 核心真正同时执行。
       - asyncio 默认是单线程、单事件循环，因此它提供的是**并发能力，而不是多核并行**。

    4. **重要边界条件**：
       - 事件循环只能在遇到**非阻塞等待**（如 `await asyncio.sleep()`、I/O 等待）时切换任务；若协程内部有**阻塞调用**（如普通 `time.sleep()`、同步 I/O），循环仍可能被卡住。
       - 异步并不保证 CPU 密集计算更快，因为单个线程不能并行算多个 CPU 任务。

    **不确定处**：资料未说明回调式 API 与协程式 API 的实现对比，也未展开 asyncio 与线程/进程并发在细节上的异同。因此以上结论只限定在官方文档已确认的范围内。

    2. **切块**：把长文本按语义或固定长度切成若干段落（chunk）。块太大会夹带无关内容、稀释相关性；块太小又可能缺少上下文。切块策略会影响检索召回率。
    3. **建索引**：把每个块转换成向量（稠密表示）并建立索引，这样在线提问时能用向量相似度快速找到最相关的几个块。原始论文里用的就是稠密索引，读取 Wikipedia 段落来辅助生成。

    关键点：**外部资料不是模型参数**——知识存放在可检索的索引中，而不是“背”在模型里。这也是 RAG 名称里“检索增强”的含义。

    一个重要的提醒：**召回相关资料**和**依据资料忠实回答**是两个不同环节，评估时要分开看。第一步主要影响“能否召回对的资料”，而“是否按资料说真话”要到第二步看。这一判断点会在第二步再展开。

    ### 第一步：离线准备

    核心思想是：**把非参数化知识（外部文档）转换成生成模型能利用的检索库**。原始 RAG 论文（Lewis 等，2020）用的就是稠密向量索引——把 Wikipedia 段落变成向量，等提问时再去匹配。

    离线阶段通常做三件事：

    1. **解析文档**：把 PDF、网页、Word 等原始格式抽成纯文本。这一步要注意保留段落结构，去掉无关的页眉页脚。
    2. **切块（chunking）**：把长文档按语义切成较小的片段。切块大小直接影响后面检索的质量：太大则命中不精准，太小则上下文不完整，往往需要按你的业务场景调。
    3. **建索引**：对每个片段做向量化（embedding），存到向量数据库里，同时保留原文和元数据（来源、标题等），方便后面检索后回查和溯源。

    ### 第二步：在线检索

    核心是把用户问题也变成一段向量，然后去离线建好的向量库里找最相似的段落。流程大致是：

    1. **问题向量化**：用同一个 embedding 模型把用户的问题编码成向量，保证问题和文档片段在同一个向量空间里可比。
    2. **召回（retrieval）**：在向量库里做相似度计算，找出与问题最接近的一批段落。这一步的目标是“**找全**”，要覆盖所有可能相关的片段，宁多勿漏。
    3. **重排（rerank，可选）**：召回的结果往往有噪声，先用轻量方法粗筛，再用更精确的模型对候选段排序，把最相关的提到前面。这一步不是必需的，取决于你的精度要求和算力预算。
    4. **筛选**：按阈值或数量截取最终要用的段落。注意：即便这一步做得好，也只是**召唤出相关材料**，不代表生成的回答一定忠实——这正是你的资料里强调的，检索召回率和生成忠实度要分开评估。

    需要你记住的一个关键点：**在线检索发生在提问之后**，每次提问都会重新执行一遍，所以叫“在线”。它与离线的差别不在技术上多复杂，而在于**时序**：离线是把资料摆好，在线是临场查找。

    一个重要假设：这里继续以向量相似度检索为主线讲述，但同样的阶段也有词法检索（如 BM25）或混合检索等实现，选择取决于你的场景，不是唯一方式。

    ## 三个概念要分清

    - **参数化部分**：模型的"记忆"是训练时写进参数里的，答什么不需要查资料也能张口就来，但可能过时或编造。
    - **非参数化部分**：外部资料库（论文里用的是 Wikipedia 段落），它不在模型参数里，可以随时增删更新，是"现查的"。
    - **RAG 的关键动作**：把这两者结合，让回答建立在"当时查到的资料"之上，而不是只靠参数里的旧记忆。

    ## 一个容易误解的点

    RAG 包含两步看起来相似、其实是不同环节的事：
    1. **召回（retrieval）**：能不能把相关段落找出来。
    2. **忠实回答（faithful generation）**：找回来了，模型是否真的依据它作答。

    单靠"找到了"并不保证"答得对"。也正因如此，**RAG 并不能保证零幻觉**——如果召回的段落本身不相关或包含了误导信息，生成仍可能出错。这个限制不是讲稿的推测，是论文和它对应的工程结论里都强调过的。

    ## 模型参数（参数化知识）

    - 存在哪里：训练时被写进神经网络的权重里。
    - 特点：固定、更新成本高（要重新训练或微调），可能过时，也可能“记错”而编造。
    - 类比：像一个人长期背下来的常识，张口就来，但背的是旧版本。

    ## 检索记忆（非参数化知识）

    - 存在哪里：模型外部，是一个独立的资料库（论文里用的是 Wikipedia 段落），**不在模型参数里**。
    - 特点：可以随时增删、替换，是“用的时候才去查”的。
    - 类比：像手边随时可翻的工具书，内容更新只改书，不改人脑。

    ## 关键区别一句话

    **参数是模型“自带”的、固定的；检索记忆是“外挂”的、动态的。** RAG 做的事情就是把这两者接起来：先查外部资料，再把查到的段落和问题一起给模型，让回答基于“此刻查到的内容”而非参数里可能过时的旧记忆。
