## 已复现的交接冲突（试跑停止时的 KT-03 建议）

真实路由将「补充原预览、暂时不要保存、不进入下一步」判为同一目标的 correction／reject／defer，并带一个拒绝保存的动作。`knowledge_invitation.candidates` 因存在任意 proposed action 整体返回空列表：两次回答输入的 `capture_candidates` 都为空，原预览及更新规则没有在该交接中送入回答步骤。数据本来仍有一个符合原任务、版本、纠正中状态与空记忆约束的邀请；仅在本地内存对照移除这一非提交动作，就能取到原邀请 v2。

最后一次模型 JSON 虽可解析，返回的新引文又来自旧讲解而不在本轮回答中。使用真实留存输入／输出的[零模型回放](same-topic-replay.json)确认：实际空候选必然失败；只补候选列表仍会因这三条不真实的新引文失败，不能直接放行或声称修复即可保证模型通过。原引文与版本守卫应继续保留。停止后建议下一条仅恢复「明确同点补充且拒绝／延后保存」时的可编辑预览交接，保存确认独立；本页结果及 `proposed_fix` 记录的是试跑停止／修复前状态。随后 Rex 已按决定 238 批准先实施和零新增模型受控复验，后续进度见 [KT-03](../../../work-status.md#kt-03)，不倒改本次失败或假定真实更新已成功。

原生失败回复保留了第一轮已流出的文字，其中说「我把它更新进…预览」，但实际邀请仍失效；界面同时标明回复未完成和错误，不能把这句流式内容当作更新回执。本次只据真实邀请状态判断失败，不扩展修改到全部流式表达。

## 账目、持久化与保护

20 个稳定请求身份与 SDK 实际传输、20 个 HTTP 200、20 笔回报用量一一对应；8 次探测在独立服务账本，12 次对话调用在四个 Run 中。共报告输入 115,972／输出 8,012／合计 123,984 token；无缺失用量，不将 token 当作已核账金额。

失败后立即写 STOP，没有点击手动重试或保存，没有新问题／后台实际模型调用。正常退出后，新进程读取确认 **0 卡／0 来源／0 复习、4 Run、8 条原生消息**。后台有七条完成输入／回复，另一个失败 Run 的 partial 单独保留，原生以 failed 持久化相同正文，没有当作完成回复。邀请 id／v2／invalidated 与本机投影一致；四次实际输入 POST，无重复发送。原四步学习安排及当前步骤保持未知，没有自动推进。
