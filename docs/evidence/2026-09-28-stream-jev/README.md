# 产品续聊、流式性能与 Jev 路径专项复核

2026-09-28。微信拖图由 Rex 在日常 App 中确认可用；本轮独立测试其后的产品续聊、流式输出，以及 Jev 是否实际参与决策。测试 App 使用独立临时数据库和端口，未修改日常聊天或知识库。初轮尚未替换日常构建；后续十节压力题补修已更新日常 Debug App，真实使用手感仍待 Rex 实测。

## 产品续聊

在隔离会话中设置旧 JD Task 与待选问题，再接一轮产品讨论，向真实模型单独发送“继续”。两次重复均以最近产品讨论为依据继续回答；运行 scope 为 `conversation`、材料重点为 `product`，未调用 `jd_analysis`，旧 Task 和待选问题保持不变。改动只约束未要求面试应用的产品讨论继续谈产品机制和指标，不改写历史答案。此处使用合成旧会话；未重发 Rex 的实际招聘链接或小程序材料。

## 流式输出与界面

旧构建的真实长答在持续输出时，主线程 5 秒窗口的计时器间隔 P95 达到 310–413 ms；采样显示事件处理、持久化与自动滚动布局占用主线程。本轮把 SSE 网络消费移出主线程阻塞路径，并把相邻正文快照合并为最多 80 ms 一次；阶段、停止和完成不等待正文节拍。每个事件的序号和恢复数据仍按顺序保存，随后 ACK。

新构建在原生隔离 App 中用真实 DeepSeek Flash 完成五小节产品长答，最终保存 889 字，服务运行 6.9 秒、首段约 3.6 秒；界面出现完整回答和复制按钮，服务端游标与 ACK 均为 47。回答期间的 5 秒窗口主线程计时器间隔 P95 为 19.2／36.5 ms，最大间隔为 125.3／55.8 ms；下一窗口回到 P95 17.6 ms。另一次十小节压力题输出期间窗口 P95 最高 42.3 ms，测试中的滚动和输入可响应，但该轮最终出现 `RT.MODEL.SCHEMA`，保留了部分正文并显示“回复未完成”。这仍是输出可靠性缺口，不能算长篇内容稳定完成。

这些是主线程定时器间隔与原生交互记录，不是实际帧率；旧新模型回复长度与事件数量不同，数值不能作为严格同条件提速比例。正常回复与压力场景均未重现旧版持续 300–400 ms 的停顿，最终手感仍需在 Rex 的日常窗口验收。

原生 `ConversationReplayTests` 与 `ConversationControlTests` 通过；其中 SSE 突发样例确认三个连续正文事件合并为首个全量页与后续两事件批次，恢复 checkpoint 从版本 1 连续合并到版本 3。最终 Swift 构建及签名通过。Python 定向回归 77 项通过、19 个子案例通过；有 5 条既有弃用警告。

## Jev 的实际参与边界

日常服务 `GET /healthz` 当次返回 `jev.status=off`，所以日常聊天没有执行 Jev 决策。仅在隔离 Jev 测试实例中，入口节点向 Jev 发出真实请求：概念解释样例的 Jev 结果因 `llm_reserved_or_conflict` 未被采纳，全部字段交回 DeepSeek Flash；问候样例 `applied=true`，`intent=greeting`、无需核验和无需交叉来源由 Jev 提供，workflow 与 relation 仍由程序确定，其余不确定项由 Flash 补判。两例均有 Flash 请求且整轮检查通过；不能从两例推断准确率、速度或成本收益。

图片识读仍由 Flash 处理；Jev 不看原图，也不修复最终回答 JSON。最终输出结构依赖 Responses JSON Schema、服务端校验和一次修复，压力题已证明这个链路仍可能失败。本次没有改变日常 Jev 开关或提供商配置。

## 十节压力题补修与日常 Jev 开关核因

原失败事件的两个 `model_attempt_failed` 诊断分别为 `learning_plan.steps` 超过 8 项，以及 `learning_plan.steps` 与 `step_ids` 均超过 8 项。入口当时把一次性产品文章判为 `goal / topic_exploration / direct_teaching`，因而模型生成内部学习计划；用户要求的十个正文标题被误复制成十个内部步骤。它不是输出 token 用尽，也不是客户端把已经成功的回答截断。

补修将一次性交付的文章、报告或指定标题数完整分析识别为直接回答；明确分段教学、课程、练习或检查仍保留学习任务。结构修复提示增加数组元素上限及“正文标题不等于内部学习步骤”的说明，未放宽 `LearningPlan` 的 8 步约束。沿用原句的三次真实 DeepSeek 隔离回放都完成：均为 `question / conversation / answer_only`，零新任务、零格式失败，十节全部出现，正文分别为 1390、1324、1720 字；第三次每节都包含用户行为、可验证指标和边界情况。约 2000 字仍有偏差，但第三次达到约 86%，不将其写成严格字数命中。明确要求系统学习并教第一段的对照仍为 `goal / learning / source_learning`，生成一个学习任务并从 `lesson` 节点完成。结构修复定向测试同时覆盖内部两个数组超长与用户正文不进入诊断。

Jev `off` 是已有设计而非服务异常：正常 Mac App 以 8742 端口启动服务时显式传 `REVIEW_TODAY_JEV_TEST=0`，Python 服务默认也为 0；即使强行设置为 1，服务端仍拒绝在日常 8742 端口或非隔离数据库启用。只有 `tools/run_jev_app_test.command` 的独立临时库、非日常端口测试 App 能打开它。项目原先把 Jev 定义为局部判断的隔离试点，整轮准确性与成本收益尚未达到日常接管结论；本轮没有改变该产品决策，也没有读取或复制 Jev 凭证。

补修后的 Python 回归为 115 passed、19 subtests passed（另有 5 条现有弃用警告），Debug 构建与签名通过。重新打开当前日常开发 App 后，`/healthz` 为 `ok`，Jev 仍 `off`；原 JD 会话可打开，今天页仍有 8 条知识，没有向日常聊天发送测试题。历史失败回答保持原样，用户可在 Agent 新会话用同一十节请求验收新版行为。

后续检查发现旧失败 Run 的重试会沿用旧意图缓存，因此又提升对话策略版本，并限定清理“同一 Run 误建、没有学习进度、重判后为普通问答”的旧任务。第一轮副本重试虽重新调用 Flash，却仍把自己上次失败时误建的任务当作先前目标，生成了 180 字的错误承接；这条失败保留为根因证据。随后只在这种同一 Run、无学习进度的重判中移除旧任务与派生会话目标，仍保留原用户输入。第二轮使用原十节失败会话的隔离数据库副本显式重试，完成 `question / conversation / answer_only`，原误建任务标记 `routing_corrected / cancelled`，生成 2264 字、十节各含用户行为、可验证指标与边界情况，没有 JD 或面试内容。原数据库及日常数据未被测试写入。

最终相关 Python 回归 128 passed、23 subtests passed；覆盖原 JD 失败重试仍保留同一个有效任务，以及文章失败重试撤销无进度误建任务。正常日常 App 再次重启后服务 `ok`、Jev `off`，原 JD 会话可打开，今天页仍有 8 条知识。旧用户会话的实际重试按钮未被代理点击；Rex 可以在对应失败卡片上实测，历史失败输出会保留作为记录。
