## 检查结论

| 对象 | 文档与实际机制 | 本批证据 |
|---|---|---|
| 后台摘要 | Harness 维护预算与 Run 账本已有；单次整理共享 90 秒／两次实际发送；维护准入十二次／180 秒／累计估算输入 512,000。完成回复不继承整理失败，发布受上下文、归档与引用守卫约束 | 八个摘要场景：独立成功、缺失未知、请求失败、调用／输入／时间到限、归档迟到回报、跨批次共享尝试 |
| 能力探测自动恢复 | Harness §17.1 明确允许 10／30／120 秒后继续每 120 秒探测；仅重检临时失败角色、单飞、401／403 不自动重试；每步骤默认 45 秒并共享最多两次实际发送，整批没有总轮数上限 | 三个不同模拟模型八轮连接失败，SDK 替身累计二十四次发送，仍排下一轮；时间为受控时钟，无真实等待或供应商调用 |
| 能力探测用量 | `model_is_callable` 与 `model_stream_capability` 都未传入 on_request／on_usage，没有服务级账本；当前前台 Run 用量不能代表这些后台请求 | 兼容分支三模型结构化＋教练流式四请求，DeepSeek 同模型分组智能／深入结构化＋两流式四请求，各四次合成 usage 均未交给回调；不是日常真实费用证明 |

摘要既有维护上限与共享单步上限同时生效。在小窗口多批次场景中，共有三笔节点准入、**两次实际 SDK 请求**，第三笔零请求被 `ATTEMPTS_EXHAUSTED` 拦住；不把预留节点当第三次真实计费。摘要没有完成则覆盖范围不前进，原消息和已完成回复均保留。

归档可让调用者提前放弃等待；迟到已知 usage 仍能补原账本，而摘要不发布。最终报告等该受控传输结算后采样，不把调度结束与上游真正结束混同。
