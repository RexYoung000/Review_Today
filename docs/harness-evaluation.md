# Harness 质量评测与飞书工作台

2026-09-08，Rex 已批准实施。产品规则以 `agent-harness-v2.md` 为准；本文件定义评测系统，不自动修改产品行为，不代表 M1 验收或 M2 放行。

## 使用目标与边界

评测运行器自动执行场景、记录回复和状态、判分、聚合失败并同步飞书。飞书是日常查看与人工复核入口；Git 保存样本、参考材料、评分标准和运行器。评测本身不会训练模型或自动修复产品。发现问题后生成证据与修复方向，Rex 确认后才实施对应产品修复。人工反馈和线上失败先作为候选样本，审阅后版本化，不能自动修改标准以提高通过率。

## 样本与评分

初版 40 个合成但贴近 Rex 的 AI、技术与产品学习场景，Auto、知识整理、资料学习、主题探索、问题攻克各 8 个，每模式至少 3 个多轮；涵盖事实、概念和流程知识。30 个开发样本、10 个冻结留出样本，近似变体按场景族划分，留出集不得用于反复调参。先运行 12 个开发样本校准，完整基线再运行全部 40 个。留出已暴露的失败不能仍称为未见样本，后续优化需补新留出版本。

每个样本包含用户目标、固定用户轮次、来源包、必须与禁止行为、期望状态、关键断言及评分重点。不把准确路由/答案注入生产模型；从真实 ConversationHarness.accept / drain 运行，模型保持项目当前配置。只替换公开检索/页面读取边界为固定资料包，记录所用资料、查询和实际调用。另有显式 online 运行，与固定来源基线分开统计。资料包是人工编写的固定参考摘述，不伪装成实时原文抓取。

规则判定负责可客观检查的副作用/状态/版本门禁。独立调用 DeepSeek Pro 作为初版裁判，基于可见记录和参考标准对意图满足、正确性、产品边界、教学质量、依据诚实、表达可用性评分：0 明显违背，1 有实质缺陷，2 满足，3 优秀；证据不足转人工复核。裁判不能看生产模型的隐藏推理，不能替代人工校准；同厂模型相关偏差仍存在。语义严重错误必须引用实际回复作为证据。规则和语义评分分别保留，不用平均分掩盖硬失败。

初始门槛：40 个基础场景至少 36 通过，各模式至少 7/8；所有适用维度至少 2，硬失败为零。关键 10 个场景另外各重复 3 次，必须 30/30。未运行、运行错误、待复核均留在计划分母，不算通过。校准批、基础批、关键重复批、online 批分别展示。有限固定样本通过率不等于线上所有请求正确的概率。批次比较要求代码、样本、rubric、模型/强度、工具环境可追溯；版本差异须说明。

## 执行与证据

真实模型调用必须显式 `--live`，并设置单样本请求数和时限、批次并发及重复上限；缺少密钥或裁判失败必须如实显示。每个试验独立进程和临时 SQLite；导入服务前设置临时库路径，禁止访问正常 Mac 私人知识库。保留可见消息、投递/步骤事件、任务/草稿/理解/保存状态、工具证据、首段正文耗时、总耗时、模型请求数；provider 返回 usage 时记录，否则为空。忽略隐藏 reasoning、密钥、完整环境变量。

允许模拟 Mac 的版本绑定保存按钮、claim/ACK 协议以检查服务契约，报告必须标注 simulated_ack；该结果不能证明 SwiftData 持久化、FSRS 或原生 UI 正常。未请求保存的样本不能产生提交包；自述理解、参考答案和跳过不能标为掌握。版本修订、拒绝保存、暂停/停止、被排除记忆与来源指令隔离纳入覆盖。

本地 JSON 是每次运行的原始事实，报告可离线复算。默认只同步仓库合成数据和脱敏摘要；真实个人记录不自动上传。运行版本包含代码提交、生产源码哈希、数据/rubric 哈希、角色模型和环境标识。自动化测试使用替身验证运行器与规则，绝不作为真实模型质量成绩。

## 飞书工作台

新建专用 Base（与既有“评测接入验证”分开），使用用户已授权的飞书官方 CLI。四张关联表：

- 样本：编号、版本/分组、模式、用户目标、输入、预期、参考、关键标记；人工维护候选变更备注。
- 评测批次：版本、时间、批类型、计划数/通过/失败/错误/待复核/未运行、通过率、门槛、模型和报告位置。
- 结果明细：稳定试验键、关联样本/批次、机器结果、各维分数、规则失败、回复与证据、耗时、调用数；人工结论/原因独立保留。
- 问题处理：稳定问题键、关联样本/首次结果、问题分类、证据、建议检查入口、处理状态、人工确认/备注。

仪表盘展示批次通过率趋势、通过/失败/错误/待复核数量、各模式表现及问题分类。机器评分与人工复核分开。以稳定业务键查重后写入；网络结果不确定时重新读取再重试，不能盲目再次新增。同表写入串行、分页完整、每次同步回读数量及关键值，保留人工字段。同步失败保留本地结果，可安全重跑。初版不建消息通知、定时器、云端执行或自主修复。

## 验证与交付

完成后记录运行器测试、既有服务回归、飞书同一批次重复同步无重复的回读、仪表盘计算值与真实界面检查。首轮真实成绩无论好坏如实汇报；12 个校准样本需 Rex 抽查后，才可把模型裁判视为已校准。原生 Mac 全闭环另行验收。

## 已实现的使用入口

`agent-service/evals/` 包含版本化 JSON 样本、固定来源、rubric、真实 Harness 运行器、独立裁判、规则/门槛计算、Markdown 证据报告及飞书 CLI 同步。没有修改生产 Harness、供应商配置或原生 App。每批次自动留存数据/rubric 副本、生产源码及运行器哈希；中途改生产源码的批次不得过门槛。

从仓库根运行（使用项目现有 Python 环境）：

```bash
bash agent-service/run-evals.sh validate
bash agent-service/run-evals.sh run --live --suite calibration --feishu-config ../output/harness-evals/feishu.json
bash agent-service/run-evals.sh run --live --suite full --feishu-config ../output/harness-evals/feishu.json
bash agent-service/run-evals.sh run --live --suite critical --feishu-config ../output/harness-evals/feishu.json
```

注意：脚本进入 `agent-service`，因此 `--feishu-config` 应传绝对路径，或使用 `../output/harness-evals/feishu.json`。首次创建工作台用 `provision --config <本地配置路径>`，之后复用同一配置；不要重复创建 Base。当前工作台见 [飞书质量总览](https://my.feishu.cn/base/ZDJeb5B9na4TAgs8PDncQRMKnFh?block=blktXbRhatkjdPTQ)。配置保存 Base/表/图表 ID，不含认证令牌；认证仍由飞书 CLI 管理。

`--env-file` 可重复指定原项目 `.env` 和 DeepSeek 私密环境文件（独立工作树使用）；不复制密钥进仓库。`REVIEW_TODAY_TEST_PYTHON` 可指向已有虚拟环境 Python。默认每场景最多 40 次真实 SDK 请求（包括裁判/重试）、600 秒、并发 2；关键批固定 3 次，不无限循环。`--case <编号>` 可复现单个开发失败，单题结果不满足完整门槛。`--environment online` 显式开启真实公开网络，成绩不混入固定来源门槛。

`run --feishu-config ...` 在批次结束时自动同步；本地运行进度每个场景更新，飞书更新为批末。同步失败保留原始成绩，以 `sync <批次绝对目录> --config <配置绝对路径>` 重试；不重跑模型。`report <批次目录>` 从原始 JSON 复算本地报告。`review <批次目录> --config ...` 拉取人工意见单独保存，不覆盖机器原始分数。

在飞书：打开「结果明细 → 失败与异常」查看回复/诊断/修复入口；「人工校准」视图填写「人工结论、人工原因」。问题表从「待分析」走到「待确认修复」，Rex 确认后才进入修复；状态更改只是工作记录，不直接触发代码执行。样本表的「候选变更备注」用于提出修改，必须审阅后更新 Git 的场景/rubric 版本。误判不会自动变成新的金标。
